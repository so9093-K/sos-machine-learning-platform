# 계약

플랫폼의 공통 개념과 컴포넌트 사이의 의미를 정의한다. **정확한 필드명·타입·기본값은 구현된 코드, 스키마 및 자동 생성된 API 명세**가 원본이며 여기서 복제하지 않는다. 계약은 특정 프레임워크나 서비스 제품의 내부 객체에 종속되지 않는다.

## 핵심 개념

| 개념 | 의미와 경계 |
| --- | --- |
| **Project** | 데이터·연구·모델·권한을 묶는 작업 범위 |
| **Experiment** | 연구 목적에 따라 관련 설정·실행·평가를 비교하는 논리적 묶음 |
| **Workflow Definition** | 재사용 가능한 작업 단계, 입력·출력·의존관계의 정의 |
| **Workflow Run** | 특정 Workflow Definition을 실행한 개별 기록. 하나 이상의 Job을 포함할 수 있다 |
| **Job** | 플랫폼에 제출된 단일 실행 요청과 그 수명주기를 추적하는 논리적 단위 |
| **Execution Attempt** | Job을 수행한 실제 시도. 재시도는 이전 시도와 구분된다 |
| **Dataset Reference** | 사용된 데이터의 소스·버전 또는 재식별 가능한 범위와 스키마 |
| **Model Revision** | 식별 가능한 한 모델 결과의 불변 판본. 가변적인 배포 별칭과 구분한다 |
| **Artifact** | 모델·전처리·평가·로그 등 생성·참조되는 결과물과 무결성 정보 |
| **Evaluation** | 특정 모델·데이터·지표·평가 조건의 조합으로 얻은 결과 |
| **Runtime Specification** | 작업을 실행하는 데 필요한 환경 및 호환성 요구 |

등록형 Pipeline의 Workflow 정의·단계 의존성·Run 상태·운영 Lineage는 Dagster OSS가 관리한다. SOS의 Workflow 제출 식별·Actor 권한과 개별 Job/Attempt·불변 결과는 SOS 정본이며, MLflow는 Experiment·Model Registry의 관리 정본이다. 이 세 시스템의 ID·책임을 동일한 상태나 자산으로 취급하지 않는다.

등록형 Pipeline은 Pipeline Creator가 제공하는 신뢰된 Workflow Definition의 사용자 경험이다. 각 실행은 사용자의 Dataset 판본에 고정된 별도 Workflow Run이며, 기존 Job/Attempt·권한·불변 결과를 재사용한다. Pipeline을 이용하지 않는 독립 ML API 실행도 유지한다.

단순한 Job은 반드시 Workflow Definition에 속할 필요가 없다. 실험은 실행 자체가 아니며, Job과 실행 시도도 동일하지 않다. 모델 판본·아티팩트·배포 대상은 서로 다른 생명주기를 가진다.

모델 그룹은 목적별 논리적 Registered Model이며, 그룹의 표시 이름·설명·보관과 모델 버전은 MLflow가 관리한다. 새 학습으로 기존 고정 모델 결과를 덮어쓰지 않으며 기존 단일 그룹은 `default`로 참조한다. Registry 그룹/버전 보관은 신규 모델 사용을 제한하지만 물리 삭제가 아니다. 모델 파일의 영구 삭제는 SOS가 실제 S3 객체와 MLflow 버전 제거를 확인하고 `Deleting`/ `Deleted` 상태를 기록한다. 과거 Scoring·정책·평가·설명은 독립 실행 근거로 남고 삭제된 Model Revision은 접근 불가 모델 파일의 참조 tombstone이 된다. [ADR 0017](adr/0017-model-lifecycle.md)을 따른다.

## ML 점수·판정·평가의 독립성

- **Scoring 근거:** 학습에 사용한 동일 Dataset 판본을 점수화한 결과는 독립 검증 데이터의 성능이 아니다. Scoring 결과의 데이터 관계와 분위수 임계값의 참조 판본을 구분한다. 학습 시 고정한 UTC 시간 경계로 선택된 Calibration/Test 범위는 Dataset 원본 판본·구간·행 수를 결과 근거로 보존한다. 결과 파일의 row_index는 결과 내부 순서이며 원본 관측치 식별자가 아니다. 시간 분할 Scoring은 검증된 원본 관측 시각을 같은 결과 행에 보존하며, 참조 Pipeline의 선택적 `sos_observation_id`는 UUIDv4·고유성 검증 후에만 연결된다. 관측 시각은 고유 ID가 아니고 집계 Feature 관측치는 원시 이벤트 한 건을 보장하지 않는다. 과거 결과에 해당 필드가 없다면 임의로 연결하지 않는다. 필요한 경우 원본에 **미리 고정된 불투명 UUIDv4 관측치 ID**를 명시해 Scoring Result의 별도 필드로 연결할 수 있다. 이 값은 선택한 점수화 범위 내 유효성·고유성을 검증하며, 사용자·호스트 등 업무 식별자에서 자동 파생하거나 원본 접근 권한을 대신하지 않는다. 기존 Transform Job이 UUID를 생성해 새 Dataset Revision을 게시할 수 있다. 발급 UUID는 **게시된 Dataset Revision 내부**에서 안정적이며, 같은 소스로 다시 Prepare하면 새로운 UUID가 생길 수 있으므로 재현 실험에는 게시된 Dataset Revision을 고정한다. 게시 전 Preview의 임시 결과는 정식 관측치 ID로 취급하지 않는다. 시간 구간의 비중복과 관측값 간 통계적 독립성도 다르다.
- **모델 점수와 판정:** 학습된 모델의 점수는 확률·참값이 아니다. 점수 방향·척도·모델 판본을 표시하며, 점수를 임계값과 운영 행동으로 바꾸는 정책은 별도로 판본 관리한다. 정책의 보정 Scoring Result와 정책을 적용하는 Scoring Result는 서로 다른 참조일 수 있다. 재사용은 동일 모델 판본·Feature 서명·점수 방향과 척도 및 각 결과에 대한 접근 권한을 검증한 뒤 허용한다. Scoring Result ID가 다르다는 사실만으로 데이터 구간의 비중복·독립성을 입증하지 않는다.
- **레이블과 평가:** 비지도 학습이라는 사실과 평가 레이블의 존재 여부를 구별한다. 레이블 없는 결과에 정답 기반 정확도·Precision·Recall을 붙이지 않는다. 레이블이 불충분한 경우 근거 수준과 미정의 지표를 구별한다. 정책이 없더라도 레이블이 있으면 순위 지표만 평가할 수 있으며, 이를 무레이블 평가로 표시하지 않는다. 같은 Scoring Result의 점수로 산정한 분위수 임계값은 별도 보정·검증 집합에 근거한 독립 성능을 뜻하지 않는다.
- **학습 입력과 실행 자원:** `all`은 선택한 Train 범위의 모든 행, `sample`은 명시적으로 선택한 행 수를 의미하며 실제 데이터 저장 방식이나 Worker의 RSS/임시 디스크 예산과 혼동하지 않는다. 물리적으로 수용할 수 없을 때는 실행 실패를 정확히 보고하지만, 임의의 사전 행 수 상한에 맞추려고 입력을 조용히 줄이거나 비슷한 데이터 규모에 특화하지 않는다.
- **Explanation 출력 경계:** Feature 치환 민감도와 Permutation SHAP 기여도는 서로 다른 설명 방법이다. SHAP은 모델의 실제 SOS 점수 함수(전처리 포함)·기준 출력을 설명하며, 기준값·선택된 배경·Seed·평가량·라이브러리 판본·가법 재구성 오차를 결과에 남긴다. 단일 Train 중앙값 합성 배경은 Train 관측 분포를 대표하지 않으며, 기여도는 사고 원인·확률·정답을 의미하지 않는다.
- **단계 재사용:** 이미 계산된 모델 점수를 다른 Threshold Policy에 적용하거나 설명을 별도로 생성할 때 불필요하게 다시 학습하지 않는다. 실제 재사용 가능 범위는 입력·모델·방법·Runtime 계약으로 판단한다.
- **MLflow 관리 정본:** Experiment·Run·Registered Model·Model Version의 관리 정본은 MLflow다. SOS의 Model Revision은 관리 Registry가 아닌 Job/Attempt·Dataset·아티팩트 SHA·Feature·Runtime의 불변 실행 참조이며 MLflow 고정 버전을 연결한다. 등록되지 않은 신규 모델은 Scoring에 사용할 수 없다. Job/Attempt와 Evaluation의 결과 의미는 MLflow가 대체하지 않는다.

Dataset 없는 단일 관측치 Playground Job은 입력 Feature와 실제 모델 점수를 Job 명세·결과로 보존한다. 배치 Scoring Result 또는 독립 평가를 생성하지 않으며, 모델 판본·Actor 권한·Registry·입력 서명·Runtime을 동일하게 검증한다. Playground의 Job 이력 보존은 일시적인 UI 입력과 별개이며 API 소비자에게 명시되어야 한다.

## ML 기능별 책임과 공통화 경계

![Data & Feature, Training/Execution, Scoring/Prediction, Evaluation, Decision Policy, Explanation의 역할과 공통화 범위를 비교한 표](references/ml-capability-responsibility-boundaries.png)

표의 공통화 정도는 모든 모델·방법에 같은 연산, 출력 형태, 지표 또는 설명 기법을 강제한다는 의미가 아니다. 영역마다 식별·출처·판본·권한·실행·결과·감사와 같은 플랫폼 계약을 공유하되, 실제 지원 능력과 입력·출력 의미는 모델과 방법에 따라 명시한다. Scoring/Prediction의 점수 의미, Evaluation의 지표, Decision Policy의 적용 여부, Explanation의 방법과 해석은 서로 독립적으로 검증하며 **특정 기능을 모든 모델의 필수 단계로 가정하지 않는다**.

## 모든 경계에서 지킬 규칙

- **식별과 연결:** 요청, 실행 시도, 입력 데이터, 모델 판본, 평가, 아티팩트와 Runtime을 안정적 식별자·참조로 연결한다.
- **결과의 보존:** 이미 생성된 모델 판본·평가 결과·아티팩트의 의미를 조용히 덮어쓰지 않는다. 재실행과 재평가는 새로운 기록으로 남긴다.
- **입출력 명시:** 데이터·모델 계약에서 형태(Shape), dtype, 컬럼, 시간 기준·타임존, 결측 및 값의 단위를 필요한 범위에서 표현하고 검증한다.
- **작업 의미:** 접수, 상태, 취소, 재시도, 오류의 의미는 [Workflows](workflows.md)와 일치해야 한다. 외부 API에서 중복 제출의 위험이 있는 작업은 멱등성 정책과 그 범위를 명확히 한다.
- **오류와 접근:** 기계 판독 가능한 오류 종류와 사용자 친화적 설명을 구분한다. 외부 시스템·에이전트도 동일한 권한·검증 규칙을 따른다.
- **호환성:** 후방 호환 가능한 확장과 호환성을 깨는 변경을 구분한다. 호환되지 않는 변경은 명시적 계약 식별 또는 마이그레이션 경로 없이 조용히 적용하지 않는다. 단, 사용자가 없고 외부 호출자가 존재하지 않는 사전 출시 단계에서는 명시적으로 승인한 구형 계약을 제거하고 코드·UI·테스트를 일괄 전환할 수 있다. 현재 CI는 [Testing & CI](testing.md)에 명시한 검증만 수행하며, 검증하지 않은 호환성 변경은 PR 리뷰에서 별도로 판단한다. 이 정책은 프로젝트 버전 `0.0.1`과 별개다.
- **Runtime 독립성:** 프레임워크가 다르다는 이유만으로 공통 플랫폼 계약의 의미가 바뀌지 않는다. 다만 모델 파일이 모든 Runtime에서 읽힌다고 약속하지 않으며 호환성을 명시적으로 검증한다.

이 문서는 계약의 **의미와 지속 조건**을 정의한다. 세부 API 엔드포인트·필드 목록, 플러그인 SDK와 직렬화 형식은 실제 구현·검증과 함께 정의한다.

## UI 권한·표시 설정 계약

- 사용자 화면의 기능 가시성은 인증 API에서 서버 역할 정책으로 계산한 `capabilities`를 사용한다. UI 제어는 편의 기능이며 서버의 Action 검사가 최종 권한 정본이다.
- 인스턴스 표시명(`display_name`)은 영속화된 작업 공간 표시 설정으로, 제품 브랜드와 인증 모드·배포 환경 의미를 갖지 않는다. 인증 모드는 `/api/v2/auth/me`를 정본으로 사용한다.
- 제품 브랜드명(`brand_name`)은 설치 인스턴스의 사용자 표시 설정이다. 로그인 전에는 브랜드명만 공개 조회할 수 있고, 변경은 `instance.configure` 권한과 감사를 따른다. 기본 브랜드명은 SOS이며 내부 패키지·API 식별자·환경변수·오류 코드 및 데이터·모델 식별자와 독립적이다.

## 탐색 후보와 분석 실행 계약

- Dataset Understanding의 후보는 업무 목적에 대한 권고가 아니라 입력 데이터 특성으로 구성한 **실행 가능한 탐색 조건**이다. 후보의 생성 근거·원본 Dataset 판본·프로파일 범위와 실제 Exploration의 계산 범위를 분리한다.
- 후보를 선택해도 계산하지 않는다. 선택된 `ExplorationSpec`는 탐색 화면에서 편집할 수 있고, 직접 작성한 조건과 동일한 API로 실행한다. 전체 분석은 기존 Job 계약을 통해 별도로 제출한다.
- 탐색 초안은 Dataset 판본에 귀속한다. 다른 Dataset의 결과를 이전 선택과 섞지 않는다. 구체적인 API 필드는 구현·생성 명세가 정본이다.

## 구분 텍스트 Dataset 해석 계약

파일 원본의 바이트 무결성과 Dataset의 **입력 해석 설정**은 다른 개념이다. 동일한 원본 바이트라도 헤더 유무 등 해석 조건에 따라 다른 Dataset 참조를 만들 수 있다. 등록 시 확정한 해석은 Preview·Profile·Worker·Feature 계산에 일관되게 적용한다.

현재 지원하는 탭 구분 텍스트는 헤더 유무를 명시해 등록하며, 자유 서술 TXT나 미지원 인용 방언·인코딩·열 구조를 임의로 추측하거나 복구하지 않는다. CSV는 UTF-8·쉼표 구분·첫 행 헤더로 고정하며 구분자·헤더·앞부분 건너뛰기를 자동 감지하지 않는다. 텍스트 파일은 등록 시 전체를 검사해 인코딩·고유한 컬럼명·일정한 열 개수를 확인하고, 통과한 경우에만 데이터 행 수를 함께 기록한다. 탐색 엔진과 Worker가 같은 파일을 서로 다른 컬럼·행으로 해석할 수 있는 입력은 등록 단계에서 거절한다. 정확한 업로드 형식·컬럼명과 오류는 API 구현과 테스트가 정본이다.

## Dataset Understanding 결과 계약

Dataset Understanding은 Dataset 자체가 아니라 특정 원본 판본과 프로파일 알고리즘·샘플링/전체 분석 범위에 대한 **불변 결과**다. Job/Attempt가 실행의 정본이며 성공한 Profile은 별도 참조로 확정된다. 동일 원본에 대한 재계산은 기존 결과를 덮어쓰지 않는다. 행 수·결측·고유값 계산의 범위와 정확도(정확/근사)는 독립적인 속성이다. 컬럼의 역할은 근거가 있는 후보이며 확인되지 않은 업무 의미나 Target으로 확정하지 않는다. 사용자에게 제안하는 분석은 현재 API가 검증·실행할 수 있는 정의여야 하고 변환은 사용자의 선택을 필요로 한다. 탐색 제안을 생성한 입력 범위와 제안을 실행하는 인터랙티브 표본의 범위가 다르면 사용자에게 구별해서 안내한다.

## 분석 결과의 범위·근거 계약

데이터를 **미리보기**로 조회하는 행 수 제한, **부분 데이터 분석**의 선택 방식, **전체 데이터 분석**의 입력 범위는 서로 다른 의미다. 분석 결과의 근거는 (1) 원본 Dataset과 판본, (2) 전체/부분 입력 범위와 데이터 선택 방식, (3) 요청 한도와 실제 분석한 행 수의 구별, (4) 개별 지표의 정확·근사 계산 방식, (5) 반환·표시된 결과의 제한으로 분리한다. 제한 조회는 명시적인 정렬 없이는 대표 표본이나 원본의 첫 N행으로 표현하지 않으며, 무작위 표본도 대표성을 보장하지 않는다. **전체 데이터 분석은 모든 통계값이 정확함을 뜻하지 않고**, 전체 그룹 집계와 일부 그룹 표시는 공존할 수 있다. 미계산·미확인 정보는 0이나 정확한 값으로 대체하지 않는다.

현재 Understanding은 원본 판본·선택 방식·Seed·알고리즘 판본·실제 분석 행 수를 제공한다. Discovery Profile은 제한 조회와 실제 분석 행 수를, Exploration은 분석 범위·조회 상한·그룹 표시 제한을 제공하되 실제 분석 행 수나 선택 알고리즘 판본은 응답에서 보장하지 않는다. **현재 응답에 없는 근거는 UI가 추정해 채우지 않는다.** 선택 알고리즘·표본 정책이 가변화될 때에는 이전 결과의 근거를 재해석하지 않도록 실행 시점의 방식·설정·알고리즘 판본을 결과에 결부시키고, 기존 필드의 의미를 변경하지 않는 호환 가능한 계약 확장을 우선한다. 결과 비교는 Dataset 판본·조건·선택 방식·계산 방법이 비교 가능할 때에만 성립한다.

## 데이터·실행에 적용하는 계약

- **Dataset:** 파일은 검증된 내용 무결성으로, Iceberg Dataset은 고정 Snapshot으로 입력 판본을 식별한다. 합성 예제도 실제 Dataset 참조를 사용하며 조용히 등록하지 않는다.
- **Discovery:** 미리보기와 전체 Job 분석의 입력 범위·반환 한계를 구별한다. NaN·Infinity와 실제 NULL, 큰 정수·DECIMAL의 정밀도, 바이너리·시간 값은 의미를 잃지 않도록 표현한다. 비유한 집계는 그룹 정렬·제한 이전에 정규화하며, 실제 API 직렬화 형식은 구현과 응답 명세가 정본이다.
- **Feature:** Lag·Rolling의 시간 정렬·그룹 경계와 계산 범위를 보존한다. 동기 미리보기에서 전역 연산을 잘린 입력으로 대체하지 않으며, 위험한 임의 SQL·파일 경로를 쿼리 입력으로 받지 않는다.
- **Job 제출:** 외부 중복 요청이 위험한 작업은 Actor·명세·멱등성 키의 범위를 지킨다. 실행 중 외부 커밋이 불명확한 Iceberg 적재는 자동 재시도하지 않는다. [Workflows](workflows.md)가 실행 상태를 정의한다.
- **OpenAPI:** 서버의 Pydantic 모델과 생성 OpenAPI를 웹 타입의 정본으로 삼는다. 정확한 API 필드·페이지 한도와 계산 구현은 코드·스키마·테스트를 따른다.

## Iceberg 테이블 쓰기 권한

- 테이블에 대한 쓰기 권한은 `datasets.owner_actor`로 표현되는 Snapshot 읽기·연결 권한과 독립적이다. 신규 테이블명 예약은 Job 멱등성 확인과 동일 PostgreSQL 트랜잭션으로 확정하여, 실패한 중복 요청이 다른 이름을 선점하지 않도록 한다.
- 신규 테이블은 PostgreSQL의 고유 이름·소유 Actor·무작위 토큰을 먼저 예약하고 실제 Iceberg Catalog Table Properties의 동일 토큰과 물리 Table UUID를 고정·검증한다. 같은 이름·토큰으로 다시 생성된 다른 UUID의 테이블은 기존 소유권을 재사용하지 못한다. 다른 Actor의 이름 충돌은 거부한다.
- API 제출 및 Worker 외부 커밋 이전의 실제 Table 메타데이터를 모두 검증한다. 미확정·소유권 불명·토큰 불일치·소실된 기존 테이블에는 쓰기를 허용하지 않는다. 기존 Snapshot 참조와 Tag는 그대로 유지한다.
- 테이블 쓰기 소유권은 현재 한 Actor에게 귀속하며, administrator의 조회 권한을 자동 append 허가로 해석하지 않는다. 쓰기 토큰이 없거나 소유권이 불확실한 기존 테이블은 읽기·보존만 허용하며, 관리자에게도 소유권 채택·이전 권한을 제공하지 않는다. 데이터의 추가 적재가 필요하면 권한이 확인된 기존 Dataset을 입력으로 신규 테이블명에 별도 적재해 새로운 소유권을 확정한다.

## Actor·보존 참조 계약

인증 제공자가 달라져도 검증된 Actor·Action·Resource에 대한 접근 판단 의미는 유지한다. 기존 데이터의 소유자가 기록되지 않았다고 해서 최초 접근자가 자동 소유자가 되지 않는다. Iceberg Dataset의 Snapshot ID는 읽을 판본을 식별하며, 실제 보존 상태는 Catalog에서 Tag 참조와 만료 정책을 재확인해야 한다. 보존되지 않은 과거 Snapshot은 사용 가능과 보존 보장을 혼동하지 않는다. 자세한 운영 결정은 [ADR 0003](adr/0003-snapshot-identity-audit.md)을 따른다.

Playground 실행 이력의 모델 판본 필터는 DB에서 Job 페이지네이션 전에 적용한다. Actor 권한에 따른 실행 이력 가시성은 유지하며, 다른 모델의 실행 때문에 현재 모델의 이력을 누락했다고 표시하지 않는다.
