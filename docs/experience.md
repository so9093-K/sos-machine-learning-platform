# 사용자 경험

사용자 경험은 화면을 만드는 마지막 단계가 아니라, 기능의 경계·상태·API 계약을 결정하는 설계 입력이다. 기능은 사용자 목표와 성공 기준을 먼저 이해하고 UX, 계약, 구현, 검증을 반복해서 맞춘다. [제품 정체성](vision/PLATFORM_IDENTITY.md)의 Fork·Compare·Reproduce·Understand·Explore·Apply는 연구 경험의 기준이다.

## 이용자별 경험

![모델 개발·운영과 모델 체험·사용의 두 경험](references/builder-consumer-experience.png)

Builder / Operator는 모델·실행·평가·배포를 관리하고, Consumer / Explorer는 모델의 목적·제약·입출력을 확인하고 체험한다. 이는 고정된 계정 유형이 아닌 **사용 목적과 권한에 따른 경험의 차이**이며 한 사람도 두 경험을 모두 사용할 수 있다. 두 경험은 동일한 모델 판본과 평가 근거를 참조하지만 허용된 조작과 노출 정보는 다르다.

![연구 경험·모델 운영 경험·모델 사용 경험의 사용자 목표와 질문](references/research-operations-model-experiences.png)

| 이용자 | 핵심 경험 |
| --- | --- |
| **Human** | 데이터 탐색·모델 개발·평가·배포 운영 또는 모델 소개·Playground·API 체험을 목적과 권한에 맞게 활용한다. 기술적 세부 정보는 필요할 때 단계적으로 제공한다. |
| **External System** | 명확한 요청·응답, 비동기 작업 식별, 상태 조회, 구조화된 오류, 중복 요청 처리와 예측 가능한 호환성에 기반해 연동한다. |
| **AI Agent** | 사람이 쓰는 핵심 기능을 공통 API·도구 계약으로 발견하고 사용할 수 있어야 한다. 작업의 권한과 부작용, 상태, 결과를 기계적으로 판독할 수 있어야 한다. |

웹 UI는 공통 플랫폼 기능을 활용한다. 특정 화면만 사용할 수 있는 숨겨진 핵심 기능이나 UI에 종속된 실행 계약을 만들지 않는다. API-first가 웹 사용성의 대체물은 아니다.

## 모델 활용과 연구·실험의 진입

홈과 전역 메뉴는 데이터 탐색·모델 활용·연구·실험을 독립적인 목적으로 제공한다. 모델 활용은 등록 판본 선택에서 입력 확인·실행·결과 이해로 이어지며, 평가·판정·설명은 활용 문맥의 결과 도구로 제공한다. 새 학습과 모델 그룹 설정은 연구·실험 안의 행동이다. 모델 활용·연구·학습 사이에서 URL의 선택 Dataset과 모델 그룹을 유지하며 전역 메뉴의 일반 클릭·새 탭 열기에도 같은 이동 문맥을 적용한다. 기존 학습·결과 직접 주소도 계속 사용할 수 있다. 등록 모델의 독립 실행과 활동 이상 탐지 전용 분석은 화면 설명으로 구별한다.

연구 화면은 MLflow에 기록된 실행 조건·핵심 지표 비교와 SOS 실행 결과의 연결을 제공한다. 선택한 연구 묶음은 연구·학습 이동과 직접 URL·새로고침에서 복원하며, 새 학습에는 확인된 연구 표시 이름을 초기값으로 전달한다. 선택한 연구를 확인하지 못하면 기본 실험으로 조용히 대체하지 않는다. 학습 조건은 사용자가 확인·수정하고 제출하며 화면 이동만으로 실행하지 않는다. 전문 실험 분석은 공식 MLflow를 활용하고, 공식 운영 UI의 로컬·운영 권한 경계를 유지한다. 학습 요청·Dataset 판본·Job/Attempt·취소·실패·결과의 실행 계약은 SOS 공통 API가 담당한다. MLflow 화면을 보거나 학습을 새로 실행하는 것이 기존 모델 활용의 필수 조건은 아니다.

## 분석 주제의 활동 이상 탐지 경험

등록된 Pipeline의 학습 유형·분석 과제·주제는 독립적인 분류 축이며 실제 제공되는 주제만 안내한다. 탐색 화면의 폴더 계층은 이러한 독립 속성으로부터 만들어지는 표시 방식이며 영속적인 분류 종속 관계가 아니다. 사용자는 등록된 예제 Pipeline을 바로 실행할 수 있고, 방법·입력 제약은 필요할 때 펼쳐 확인한다. 완료된 모델은 독립 Scoring Job으로 다른 Dataset에 적용할 수 있다. 패널을 접어도 같은 분석 내 작업 상태를 유지하며, 결과 판본에서 실제 점수순 관측치와 선택적 설명을 탐구한다. 판정 정책 없는 Scoring 순위는 확정된 이상 후보나 검증 성능이 아니다.

등록된 주제는 학습 유형·분석 과제·적용 주제를 별도 분류 차원으로 표시한다. 첫 제공 주제는 '비지도 학습 / 이상 탐지 / 활동 이상 탐지'이며 아직 제공하지 않는 분류를 빈 탐색 화면으로 노출하지 않는다. 학습 완료 후에는 Model Revision을 재학습하지 않고 호환 Dataset에 점수화하는 '모델 적용'을 선택할 수 있다. Dataset 필수 Feature 이름을 확인하되 실제 자료형·실행 제약은 Scoring Job에서 최종 검증하며, 원래 Pipeline Test 결과는 변경하지 않는다. 모델 Playground는 등록 모델의 입력 Feature를 직접 수정하고 Dataset 등록 없는 별도 Worker Job으로 소량 점수화한다. 입력값은 Job 명세에 보존되며 같은 모델의 실행 이력을 조회해 실제 점수·입력값을 다시 확인하고 비교한다. 성공한 단일 입력 Job에서도 실제 점수를 기준으로 선택적 SHAP 기여도와 Feature 치환 민감도를 각각 독립 설명 Job으로 요청할 수 있다. 설명 결과는 원본 Job·모델 판본을 참조하고 입력 편집 후 과거 설명을 현재 입력의 설명으로 취급하지 않는다. 두 설명 방법은 서로 다른 의미로 보여주고, Dataset Scoring Result 및 판정 정책과 혼동하지 않는다.

사용자는 설명이나 별도 예제 탐색을 거치지 않고 준비된 합성 예제로 모델 학습을 명시적으로 시작할 수 있으며, 실제 진행 상황과 학습·판정·Test 결과 및 후보를 이어서 확인한다. 예제 등록·입력 검사는 학습 요청의 일부이지만 명시적 사용자 행동 없이 실행하지 않는다. 처음부터 자신의 데이터를 선택하는 독립 경로도 지원하며, 자신의 데이터 사용은 첫 경험의 필수 조건이 아니다.

학습 과정과 모델의 점수 반응을 실제 근거로 표시한다. Isolation Forest에 존재하지 않는 epoch별 학습 곡선이나 정확도를 생성하지 않으며, MLflow 등록 대기와 학습 실패를 구분한다. 학습 완료 결과는 학습 범위와 모델, Calibration에서 정한 기준, Test의 실제 검토 건수·비율·분포, 평가 한계와 다음 조사 행동을 하나의 보고서로 연결한다. 내부 단계별 탭 탐색을 이해의 전제로 삼지 않으며 설정·단계별 분포·불변 판본은 상세 근거로 제공한다. Test 점수 분포의 구간을 선택하면 마지막 구간만 오른쪽 경계를 포함하는 히스토그램 정의에 따라 현재 불러온 후보 목록을 표시상 필터링하며, 전체 후보 수나 실제 판정 정책이 바뀐 것처럼 보여주지 않는다. 새 시간 분할 Scoring 결과의 관측 시각을 같은 결과 행에 보존한다. 사용자가 Dataset에 고정한 `sos_observation_id` UUIDv4가 형식·고유성 검증을 통과한 경우에만 관측치 ID를 함께 연결하며, UUIDv4 형식만으로 개인정보 비식별성을 보장하지 않는다.  과거 결과에 없던 값은 추정하지 않는다. 선택한 후보에서 실제 Feature와 Train 참조 중앙값을 비교하되 이 차이를 이상 사건의 원인·기여도로 단정하지 않는다. 관측 입력을 먼저 확인하고 기여도 계산으로 이어가며, 단위가 확인된 값은 읽을 수 있는 단위와 참조값 대비 수치로 비교한다. 비교 분포나 설명 결과가 없는 관측값에서는 사용자가 활동 그룹과 비교할 입력을 선택한다. 고정된 몇 개의 Feature를 중요하다고 암시하는 기본 미리보기로 제공하지 않는다. 실제 입력의 결측·유효성 문제는 선택 전에 알린다. 선택적으로 동일 SOS 이상 점수 출력에 대한 Permutation SHAP을 계산해 기준 점수와 Feature 기여도 합·실제 점수의 일치를 확인한다. SHAP의 단일 Train 중앙값 합성 배경은 실제 Train 분포 대표가 아니며 기여도는 사고 원인·인과효과가 아니다. 이 비교 기준은 계산 전후에 함께 표시하며, 점수 재구성 오차를 개별 기여도 추정의 정확도로 해석하지 않는다. Feature 치환 민감도는 한 항목을 기준값으로 바꾸는 추가 실험으로 제공한다. 결과가 모두 0이면 원래부터 기준값과 같은 입력이었는지, 다른 입력으로 바꿨는데 점수가 같았는지를 실제 계산 근거로 구별하며 전반적인 중요도나 인과효과로 해석하지 않는다. 원본 로그의 단일 이벤트와 집계 Feature 관측치도 구별한다. 직접 URL로 선택한 후보가 첫 페이지에 없어도 후보 번호로 조회할 수 있다.

모델 실험실의 주제 진입은 모델의 목적과 활동 변화 개념을 보여주는 홈으로 제공한다. 여기에서는 등록 모델의 적용을 중심 행동으로 제공하고, 이전 실험 확인과 새 학습은 연구·실험으로 연결한다. 사용할 모델이 없다고 확인된 경우 연구·실험에서 학습·등록 상태를 확인하도록 안내하며, 조회 실패나 남은 Registry 페이지를 실제 빈 목록과 구별한다. 예제·모델을 서버 시작 시 자동 등록하거나 학습하지 않는다. 실행 결과를 연 경우 학습 소개를 반복하지 않고 검증된 결과 요약과 후보 탐구를 우선 배치하며, 전체 분포·Feature 값·기술 근거는 필요할 때 펼쳐 확인한다. 선택 후보의 SHAP은 모델 기여의 방향과 기준값을 읽을 수 있는 너비·대비·레이블을 사용하고, 실제 점수·임계값은 축의 축약 표시와 별도로 보존한다. 과거 분석 목록과 실행 선택은 모델 실험실에서 제공하지 않고 작업 이력에서 조회한다. 홈의 최근 분석, 이력 목록, 결과 직접 URL은 각각 선택한 분석 결과로 바로 연결한다. 분석 결과에서 데이터를 확인하러 이동했다면 그 분석과 선택 후보·분석 구간의 복귀 문맥을 유지한다.

사용자 화면의 주요 이름은 '분석 주제 > 활동 이상 탐지'와 '모델 학습 / 학습 결과 / 이상 후보 / 다른 데이터에 적용'으로 통일한다. Job·Run·Registry 식별자는 기술 근거가 필요할 때만 노출한다.

### 바로 사용하기와 결과 조사

등록된 사용 가능한 모델이 있다면 사용자는 학습·Registry 관리 절차 없이 지원하는 입력 방식으로 모델을 직접 사용할 수 있다. 모델 선택·변경은 계속 가능하지만 기본 경험은 **입력 → 실제 실행 상태 → 결과**를 중심으로 한다. 처음 보는 사용자는 선택과 실행에 필요한 정보부터 확인하며, 상세한 입력 조건·설명 계산 근거·전체 Feature 값은 필요할 때 펼쳐 탐구한다. 학습 중앙값 기반 기준 입력의 SHAP·치환 민감도가 전부 0이라면 빈 순위 차트 대신 그 의미와 값을 변경해 볼 다음 행동을 안내한다. 현재 활동 이상 탐지는 단일 관측치의 입력값 체험과 활동 Feature가 준비된 Dataset의 독립 Scoring을 제공한다. 모델 활용의 첫 경험은 별도 기능 선택보다 사용할 데이터(등록 Dataset·새 파일·직접 입력)를 이해하고 시작하도록 구성한다. 시작 화면은 같은 선택을 여러 제목으로 반복하지 않으며, 등록 Dataset 선택·검증·실행을 기본으로 두고 새 파일 등록은 필요할 때 펼친다. 실행 중인 Job의 상태와 새 분석 설정은 섞지 않는다. Dataset Scoring에서 선택한 관측값을 같은 모델의 Playground 입력 초깃값으로 가져올 수 있으나, 전체 필수 Feature·자료형이 유효할 때에만 허용하며 자동 실행·자동 보정하지 않는다. 원래 Scoring Result와 선택 관측값을 유지하고 새 실험은 별도 Playground Job으로 실행해 돌아갈 수 있다. 가져온 관측값을 그대로 다시 계산한 결과는 저장된 점수의 재확인임을 알리고 값 변경을 다음 행동으로 안내하며, 원래 관측값으로의 복원과 학습 기준값 초기화를 서로 다른 행동으로 제공한다. 저장 점수와 새 점수는 같은 자릿수로 비교하되 반올림에 가려진 차이와 실제 일치를 구별한다. 단일 입력 결과는 제출 당시 비교 대상·수정값·새 점수를 함께 보존하며 이후 편집값을 과거 결과에 섞지 않는다. 선택한 모델의 검증 가능한 학습 점수 분포가 있으면 그 안에서 실제 점수 위치를 보여주고, 구간 집계로 정확한 백분위수·확률·정상 범위를 만들지 않는다. 학습 결과·모델 사용·독립 Scoring에서 새 분석을 시작하는 핵심 경험은 공통으로 제공하며 출처 모델과 원래 결과로의 복귀 문맥을 유지한다. 파일 등록은 명시적인 사용자 행동이며 Scoring 제출·완료와 구분한다. 원시 로그를 자동으로 Feature로 변환하거나 모든 사용자 데이터에 모델이 적합하다고 약속하지 않는다.

독립 Dataset Scoring은 점수 계산 완료 후 전체 관측 수, 검증 가능한 점수 분포, 점수순 관측값, 선택 관측값의 실제 입력·참조값·선택적 설명을 같은 결과 문맥에서 연결한다. 점수순 첫 번째 관측값을 자동으로 보여줄 때에는 사용자 직접 선택과 구별하며, 상단 전체 결과 집계는 개별 관측값의 선택에 따라 바뀌지 않는다. 일반 Scoring에서도 선택한 원본 시간 컬럼을 검증해 관측 시각을 행별로 보존할 수 있으며 시간 보존만으로 시간 분할 평가를 수행했다고 표현하지 않는다. 점수 분포가 보존되지 않았다면 임의로 재구성하지 않는다. 결과 화면은 관측 수·점수·분포를 판본 식별자보다 먼저 보여주고, 분포 요약 문장은 보존된 히스토그램 구간의 실제 집계로만 만들며 판정 임계값이나 사건 수처럼 표현하지 않는다. 판본 식별자는 결과 뒤에서 확인할 수 있다. 판정 정책 없는 Scoring의 관측값 순위와 Pipeline Test의 정책 기반 검토 후보는 구별한다. 모델 유형에 따라 입력·출력 경험은 다를 수 있으며, 이상 점수·Feature 설명을 모든 ML 모델의 공통 화면으로 강제하지 않는다. 조회 실패와 실제 Job 실패는 다른 상태이고 기술 오류의 ID는 진단 근거로 보존한다.

## 등록형 Pipeline 경험

![등록된 방법을 자신의 데이터로 실행하는 Pipeline Consumer와 새로운 방법을 설계·검증·등록하는 Pipeline Creator의 경험](references/pipeline-consumer-creator-experience.png)

**Pipeline Consumer(이용자)**는 등록된 분석·학습·평가 방법의 목적과 지원 데이터 계약을 확인하고 자신의 Dataset을 연결한다. 입력 적합성을 확인해 명시적으로 실행한 뒤 Run 상태·오류·결과를 이해하고 활용한다. 미리 설계된 방법을 이용하는 경험이지, 모든 내부 ML 설정을 사용자가 직접 구성해야 한다는 뜻은 아니다.

**Pipeline Creator(제작자)**는 독립적인 ML 기능과 공통 API를 활용해 새로운 방법을 설계·검증하고 필요할 때 재사용 가능한 Pipeline으로 등록한다. 연구·실험이 항상 Pipeline 등록으로 끝나는 것은 아니며 외부 연구 환경과 독립 기능을 사용할 수 있다. Consumer와 Creator는 고정된 계정 유형이나 상호 배타적인 역할이 아니라 이용 목적에 따른 경험의 구분이다.

첫 참조 Pipeline은 활동 Feature의 이름·자료형과 UTC 시간을 요구하며 서로 다른 사용자 데이터로 새 모델을 학습한다. 입력 오류를 무단 보정하지 않고 원본 데이터와 타인의 결과를 공유하지 않는다. 다른 연구·학습·Scoring 기능은 Pipeline 없이도 실행할 수 있다. 이 경험의 장기 개념적 책임 관계는 [Platform Identity](vision/PLATFORM_IDENTITY.md#pipeline-경험과-공통-실행-경계)를 따른다.

## 등록 Feature 재사용 경험

로컬 운영자는 SOS의 별도 운영 도구 링크에서 상시 실행 중인 공식 Feast UI를 열어
Entity·Feature View·Feature Service·Source 관계를 확인한다. Feature 정의 탐색은
Feast가 담당하며 SOS는 Feature 사용·조회 Job·Dataset·모델 근거에 집중한다.
공식 UI의 Catalog 정보가 SOS Actor별 접근을 보장하지 않으므로 사용자의 일반
작업 진입점으로 노출하지 않는다. 공식 UI에서 직접 Registry를 변경하지 않고,
정의 등록·폐기는 SOS Job 계약을 따른다.


사용자는 기존 Dataset에서 안정적인 Entity·시간 기준과 숫자형 Feature를 선택해
Feature Service를 등록할 수 있다. 등록 결과는 SOS Job 이력에서 확인하며
기존 등록 Feature Service를 다른 조회 시점 Dataset에도 재사용한다.
Feature 정의 등록과 조회는 별개 Job이고, 조회는 Registry의 정의를 수정하지 않는다.
성공한 조회 결과는 불변 Dataset으로 확정해 사용자가 명시적으로 모델 학습에 사용할 수 있다.
Feature 계산·조회·학습·온라인 Serving을 한 단계의 자동 작업으로 오인시키지 않는다.
미지원 자료형·UTC 시간 부재·Registry 연결 실패·권한 부족은 완료 결과와 구별한다.
등록 성공과 현재 Feast Registry의 무결성은 다르며 실제 조회 시 정의 지문을
검증한다. 사용자는 실패·취소된 등록을 포함해 폐기 Job을 명시적으로 요청할 수
있다. 과거 조회나 다른 활성 등록이 사용 중인 정의는 Registry에 보존하지만,
폐기 접수 후 새 조회는 받아들이지 않는다. 접수 전에 정상 승인된 Queued 조회는
폐기 이후에도 완료할 수 있다. 
폐기된 등록으로 신규 조회를 할 수 없다. Registry 정리 결과와 보존 이유는 Job
결과에서 확인한다.

등록·조회 입력은 선택한 Dataset의 실제 스키마에서 고르며 Entity 키와 UTC 시간형 여부를 실행 전에 확인한다. 작업 진행 중에는 같은 요청의 중복 제출을 막고, 결과에는 제출 당시의 원본을 표시한다. 등록 폐기 완료는 해당 작업이 참조한 등록에만 반영하며 다른 등록의 선택이나 과거 조회 결과를 지우지 않는다.

폐기에 실패했다고 Registry 변경이 없었다고 간주하지 않는다. 현재 화면에서 실패한 폐기는 상태 확인·재요청을 안내하며 신규 조회를 다시 허용하지 않는다. 서버의 신규 조회 차단 상태는 폐기 완료와 구별해 등록 목록에서 복원하고, 새로고침·재접속에서도 적용한다. 목록 갱신으로 선택 등록의 차단·폐기가 확인되면 선택 상태가 남아 있어도 신규 조회를 차단한다.

표시 이름으로 Source의 파일 형식을 추정하지 않는다. 기존 등록을 선택하면 원본·식별 컬럼·기준 시각·포함 Feature·과거 조회 기간을 등록 근거에서 확인하고, 조회 Dataset의 식별 자료형을 원본과 비교한다. 등록 성공 기록과 현재 Registry의 무결성 확인은 구별한다. TTL은 조회 시점에서 허용할 과거 Feature 범위이며 저장 데이터 삭제 기간이 아니다. 폐기 전에는 대상을 다시 표시하고 신규 조회 중단·과거 결과 보존·참조 정의 보존의 영향을 확인한다.

## 연구·실행의 목표 경험

모델 자산 탐색에서는 그룹 설정 편집보다 사용할 버전 선택·학습 데이터·학습 시각을 먼저 제공한다. 그룹 생성과 학습된 버전 생성을 구분하고, 선택 그룹은 독립 학습·적용 이동과 직접 URL·새로고침에서도 유지한다. 실행 비교는 같은 종류의 실행에서 시작하며 Dataset 판본·입력 범위 등 기록된 비교 조건을 지표와 함께 확인한다. 기록이 없는 조건을 추정하지 않는다.

연구 실행 비교는 모델 버전 관리와 구별해 발견할 수 있어야 한다. 현재 불러온 목록의 검색 범위를 명시하고, 비교는 달라진 설정·지표를 먼저 보여주되 전체 기록도 확인할 수 있게 한다. 기록 누락과 수치 0을 구별하며 값의 차이만으로 성능 우열을 판단하지 않는다. 연구 Run에서 연결된 SOS 작업의 현재 상태와 결과를 확인하고, 공식 운영 UI는 해당 대상의 상세 진단에 사용한다.

1. **탐색:** 이용 가능한 데이터, 입력 스키마, 품질·시간 범위 및 제약을 이해한다.
2. **준비:** 모델과 평가 방법을 선택하고 기본 설정으로 시작하되, 필요 시 고급 설정을 조정한다. 실행 전 입력과 설정의 오류를 확인한다.
3. **실행:** 작업을 제출하고 식별자를 얻어 실제 상태와 진행 단계를 확인한다. 측정 불가능한 진행률을 추측해 표시하지 않는다.
4. **이해:** 결과와 지표, 실패 이유, 사용된 데이터·설정·모델·Runtime의 관계를 확인한다.
5. **발전:** 이전 실험과 비교하고, 재현하거나 분기해 새로운 실험을 수행하며, 모델을 추론·외부 서비스에서 재사용한다.

이 과정은 연구·실행 경험의 한 예시이지, 모든 실험에 강제되는 단일 화면이나 순서가 아니다. 연구자는 탐색·평가·추론 등 필요한 단계만 독립적으로 수행할 수 있다.

## 상호작용의 원칙

- **상태와 제어:** 접수·대기·실행·완료·실패·취소 상태의 의미는 [Workflows](workflows.md)를 따른다. 취소 요청을 즉시 취소 완료로 표시하지 않는다.
- **실패와 복구:** 입력 오류, 권한 문제, Runtime 불일치, 작업 실행 실패를 구분하고 가능한 다음 행동을 제시한다. 오류 안내는 실제 원인 메시지와 다음 행동을 먼저 보여주고, 오류 코드·요청 ID는 참조 정보로 함께 남긴다. 실행 권한이 없는 사용자에게는 실행할 수 없는 행동 대신 현재 할 수 있는 일을 안내한다. 원인 불명일 때 성공처럼 표현하지 않는다.
- **Workflow 진단:** 실패가 확인된 단계와 공개 오류·재시도 정책을 한곳에 표시하고, 단계 Job의 실패가 확인되지 않으면 실패 지점을 추정하지 않는다. 운영자용 단계 로그는 해당 SOS 제출로 연결하며 Dagster 재실행과 SOS의 새 분석 제출을 구별한다. 외부 도구의 운영 권한을 SOS의 읽기·실행 권한과 동일하게 취급하지 않는다.
- **결과의 신뢰:** 평가 지표에는 비교 조건·데이터 기준·제약을 함께 제공한다. 성공한 실행뿐 아니라 실패 기록도 후속 연구에 활용할 수 있게 한다.
- **조작 가능성:** 핵심 흐름은 명료한 명칭, 접근 가능한 피드백과 예측 가능한 상호작용으로 제공한다. 화면 제목·버튼·요약은 간결한 명사형으로 표기하고, 내부 식별자·방법 ID 대신 사용자 용어를 먼저 보여준다. 과도한 인프라 설정을 첫 사용의 전제 조건으로 만들지 않는다.
- **반복 검증:** UX 프로토타입, API 계약, 실제 End-to-End 실행을 함께 검토한다. 코드가 동작한다는 사실만으로 사용자 경험이 완성됐다고 판단하지 않는다.

구체적인 UI 구성·디자인 시스템은 이 정본이 고정하지 않는다. 실제로 따라 할 수 있는 설치·실행 절차는 구현 이후 `getting-started.md`에서 제공한다.

## 첫 ML Workbench의 목표 경험

사용자는 기존 Dataset에서 직접 모델 실험을 시작하고, 명시적인 데이터·Feature·모델
설정을 확인한 뒤 실제 학습 Job을 제출할 수 있어야 한다. 완료 후 학습된 모델 판본,
점수·평가 근거, 선택한 임계값과 설명의 적용 범위를 구분해 이해해야 한다. 같은 점수에
대한 정책 비교는 재학습을 강요하지 않는다.

레이블이 없는 이상 탐지에서는 경보 비율과 점수 분포를 보여줄 수 있지만 탐지
정확도를 확정한 것처럼 표현하지 않는다. 실패·취소·실행 한계·선택적 외부 추적 실패를
각각 구분해 다음 행동을 안내한다. 이 설명은 완성된 기능을 의미하지 않으며 단일
단계 순서나 전용 화면 구현을 고정하지 않는다.

## MLflow 연구 기록·모델 관리의 사용자 경험

SOS 웹에서는 사용자 소유 Experiment·Run·모델 그룹과 버전을 검색하고 둘의 Params·Metrics를 비교할 수 있어야 한다. 모델을 새로 만드는 행동, 동일 그룹의 새 버전 생성, 사용할 모델 선택, 이름·설명 수정, 보관/복원, 영구 삭제는 구별한다. 사용자 용어는 모델 선택·모델 버전으로 표기하며 Model Revision은 내부 실행 근거다. 영구 삭제 전 실제 영향을 확인하고 진행 중 실행과 공유 아티팩트가 있으면 차단한다. 삭제된 모델의 과거 평가 결과는 남지만 재사용할 수 없다고 안내한다. 비교 조건이 다른 Run을 동등한 성능으로 오해시키지 않는다. 등록 성공한 고정 모델 버전에서 기존 SOS Scoring·평가 경험으로 이어지고, 등록 대기/오류는 학습 실패와 구분한다. Fork·Reproduce는 Dataset 판본·Feature·Seed·설정을 참조해 새 Job으로 실행한다.

기여도·민감도는 변화가 있는 주요 항목을 먼저 비교하고, 변화가 없으면 그 사실을 짧게 요약한다. 전체 수치는 이름으로 찾아 짧은 페이지에서 확인하며, 입력 편집에서도 현재 표시하지 않는 필수 값과 수정값을 보존한다.

## 처음 보는 Dataset의 이해

지원하는 데이터를 새로 등록하면 구조와 기본 메타데이터를 먼저 확인할 수 있어야 한다. 시스템은 데이터 사전 없이 컬럼별 통계·품질·역할 후보를 제시하지만, 이름 힌트 등 불확실한 판단을 확정된 업무 의미로 표현하지 않는다. 표본·전체 범위와 근사·정확한 계산 결과를 혼동하지 않으며 원시 민감값을 자동 인사이트로 노출하지 않는다.

이해 결과는 입력 Dataset 판본과 계산 방법을 추적 가능한 별도 결과로 보존한다. 분석의 실패나 취소가 원본 등록의 성공을 취소하지 않는다. 탐색 후보는 통계·자료형·역할 후보에 기반한 실행 가능한 탐색 조건으로, 사용자 목적에 대한 적합성 권고가 아니다. 후보마다 구성 근거와 프로파일 범위를 설명하며, 선택 시 탐색 화면에 조건을 전달하고 사용자 확인·수정을 거쳐 실행한다. 사용자가 선택하지 않은 변환·대규모 작업을 조용히 실행하지 않는다. 처음 보는 데이터도 첫 번째 분석을 시작할 수 있고, 데이터 이해만으로 작업을 끝낼 수 있다.

## 처음 보는 구분 텍스트 데이터

구조화된 탭 구분 텍스트는 헤더 유무와 해석 범위를 사용자가 확인해 등록한다. 미지원 형식이나 자유 서술 TXT를 임의로 표로 변환하지 않으며, 임시 미리보기와 서버 검증 결과를 구별한다. 컬럼의 업무 의미를 추측하거나 이름 변경을 강제하지 않는다. 정확한 지원 입력 형식은 [Contracts](contracts.md)와 API 명세를 따른다.

자동 분석 예시는 계산 가능하고 정보 가치가 있는 기본 질문만 제공한다. 사용자 목적을 추정하거나 컬럼의 업무 의미·Target을 자동 확정하지 않는다. Data Preparation은 탐색과 독립적인 변환 영역으로 유지하며 특정 텍스트 데이터 때문에 신규 연산을 대량 추가하지 않는다.

## 분석 근거를 이해하는 경험

결과를 처음 확인할 때에는 **부분/전체 데이터 분석 범위, 실제 분석한 행 수 또는 제한 상한, 결과의 중요한 한계**를 짧고 가까운 위치에서 설명한다. 필요할 때 선택 방식·Seed·Dataset 판본·알고리즘 정보를 펼쳐 확인할 수 있어야 한다. 정확도는 개별 지표에 적용하며 전체 분석이라는 이유로 정확한 결과라고 일괄 표시하지 않는다. 그룹 일부만 반환·표시하는 경우 분석 대상 자체가 일부였던 것처럼 오해시키지 않는다. 제공되지 않은 실제 처리 행 수·계산 방법은 추정해서 채우지 않고 확인 불가 상태로 표현한다. 일반 사용자를 기술 용어로 압도하지 않으면서 전문가가 근거를 확인할 수 있게 하고, 전체 Job 제출은 항상 명시적 사용자 행동으로만 시작한다.

## Data Workspace의 첫 사용

현재 Data Explorer는 **데이터 이해·조회·탐색**을, Data Preparation은 Feature·Transform·Iceberg 적재를 담당한다. 각각 독립적으로 시작할 수 있으며 Dataset 참조와 Job 이력은 공유한다. Jobs·Storage·Audit 등 운영 기능은 권한에 맞춰 제공한다.

데이터가 없는 화면에서는 파일 가져오기·Iceberg 연결·출처가 명시된 합성 예제를 선택할 수 있다. 예제는 **사용자 선택 없이 등록하거나 실행하지 않는다**. Dataset을 등록하면 원본의 규모·스키마·판본을 먼저 확인할 수 있고, 별도 프로파일이나 전체 집계 Job은 사용자가 명시적으로 실행한다. 등록 성공·분석 실패·취소는 서로 다른 사건으로 표시한다.

Preview·EDA·프로파일은 실제 요청이 필요한 화면에서만 조회하고, 같은 Dataset과 조회 판본의 결과는 재사용할 수 있다. 사용자가 조건을 수정했지만 실행하지 않은 상태와 마지막으로 적용한 결과를 구별한다. Dataset을 전환하거나 새 요청이 앞선 요청을 대체하면 과거 결과가 새 Dataset의 내용처럼 보이지 않게 한다. 단, 같은 Dataset을 재조회할 때에는 편집 중인 Feature·컬럼·축 선택을 불필요하게 잃지 않는다.

선택한 Dataset은 직접 URL·새로고침·뒤로 가기에서도 유지하며, 목록의 첫 데이터로 대체하지 않는다. 목록 조회와 선택 데이터 조회의 실패를 구별하고 각각 재조회할 수 있어야 한다. 좁은 화면에서도 본문에서 현재 데이터를 확인하고 바꿀 수 있다. 탐색의 기본 화면은 분석 조건과 결과에 집중하며 전체 컬럼 통계는 선택적으로 열어 검색·페이지로 확인한다.

부분 데이터·전체 분석·표시된 행 수를 혼동하지 않는다. 정확한 정수·DECIMAL·NULL·비유한 값과 통계 한계는 오해되지 않게 제시하고, 차트는 선택한 값과 축이 의미 있을 때만 표시한다. 그룹 제한이나 미확인 계산 근거는 숨기지 않는다. Preview 실패와 Job 실패에는 각자 복구 경로를 제공하고, 완료한 Job은 전역 이력에서 다시 찾을 수 있어야 한다.

작업 이력은 짧은 목록과 선택한 작업의 상태·결과로 구성한다. 제출 후에는 해당 작업을 바로 선택하며, 직접 URL의 작업은 현재 목록 페이지에 없어도 독립적으로 조회한다. 조회 실패를 작업 실행 실패나 빈 이력으로 표시하지 않고 마지막 확인 상태와 재조회 경로를 제공한다. 분석 원본과 새로 생성한 결과 Dataset의 이동도 구별한다.

설치 인스턴스의 제품 브랜드명은 로그인·탐색·홈·브라우저 제목 등에 일관되게 표시하고, 인증 이전에도 브랜드명만 조회할 수 있다. 브랜드 정보를 조회할 수 없으면 임의의 고객 브랜드로 오인시키지 않고 중립적인 표시와 재조회 경로를 제공한다. 인스턴스 표시명은 브랜드·인증 모드·배포 환경과 별개의 서버 설정이다. 변경은 관리자 권한과 감사를 따르며, UI에서 권한을 숨겼다는 사실만으로 서버 권한 검사를 대체하지 않는다. 현재 구현의 탭·기본 컬럼 수·페이지 제한·API 필드는 코드와 자동 생성 명세가 정본이다.

## 저장소 보존·진단 경험

저장소 상태 화면은 기본 보존값, 실제 적용값과 설정 출처, 마지막 성공 검사 시각 및 현재 보이는 페이지 범위를 표시한다. 재검사에 실패하면 마지막 결과가 현재 상태가 아님을 명시한다. 소유권 확인과 데이터 보호를 우선하여 **보호 중·관측 대기·검토 후보·확인 필요**를 명확하게 구분하고, 오류에는 객체 삭제가 수행되지 않았음을 알린다. 검사와 삭제는 별도 작업이며, 현재 서비스는 검사만 제공한다. 삭제 승인·삭제 직전 재검증 기능이 없는 현재 단계에서는 삭제 제어 UI를 제공하지 않는다. 보안 감사 조회와 실제 데이터 삭제 권한은 별도 계약이다.

## 접근·보존 경험

읽을 수 있는 Snapshot과 실제 Tag가 확인된 보존 Snapshot을 구분한다. Snapshot 목록 조회는 해당 Iceberg Dataset 소유권 또는 운영 진단 권한으로 제한한다. 타 사용자의 테이블 이름을 추측해 Snapshot에 연결하는 것은 허용하지 않는다. 보호 미설정 Dataset을 무조건 보존된 것으로 표시하지 않는다. 로그인·권한 없음·보존 실패·감사 조회 상태를 사용자에게 분명하게 전달한다. 개발자 기본 신원은 로컬에서만 사용하며 운영 토큰은 브라우저 저장소에 기록하지 않는다.

모델 기준 입력 벡터가 없는 판본은 처음부터 직접 입력을 활성화하며, 이전 실행 기록은 선택한 모델 판본으로 서버 측 필터링해 정확한 페이지를 제시한다.
