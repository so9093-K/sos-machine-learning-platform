# 0001 — Dataset·Job 결과 게시의 저장소 간 일관성

- 상태: Accepted · 결과 객체 즉시 보상 삭제 조항은 [0002](0002-object-lifecycle.md)가 대체
- 범위: Data Workspace의 파일 Dataset 등록과 Transform Job 결과 게시

## 배경

Dataset·Job 메타데이터는 PostgreSQL, 원본 파일과 변환 결과는 S3 호환 객체 저장소를 사용한다. 두 서비스 사이에는 공통 ACID 트랜잭션이 없으며 DB 완료 기록 전후에 S3 객체가 이미 존재할 수 있다. 콘텐츠 해시를 키로 사용하는 업로드 파일은 서로 다른 Dataset이 공유할 수 있으므로 DB 실패만으로 삭제할 수 없다.

## 결정

1. PostgreSQL 트랜잭션을 Dataset 등록과 Job 완료 상태의 권위 있는 기준으로 삼는다. S3 전송 성공 자체를 Job 성공으로 간주하지 않는다.
2. 원본 업로드는 내용 기반 SHA-256 키를 유지한다. DB 등록 실패 시 공유 객체를 보존하며 동일 콘텐츠 재등록을 허용한다.
3. Transform 결과는 Job UUID로 구분된 독점 키를 사용한다. DB 완료 기록 실패 또는 취소 경합 시, 해당 객체를 참조하는 Dataset이 없음을 PostgreSQL로 확인할 수 있을 때만 보상 삭제한다. 확인이 불가능하면 데이터를 삭제하지 않는다.
4. 미완료 일반 Job은 Worker 재시작의 복구·재실행 대상이다. 외부 Iceberg Snapshot 커밋은 자동 재시도하지 않는다.
5. 객체 참조가 없다는 판단만으로 기존 객체 저장소의 전체 접두사를 삭제하거나, 임의의 오래된 캐시와 운영 볼륨을 정리하지 않는다.

## 근거

원본과 결과의 소유권을 구분하면 데이터 손실 없이 실패를 수습할 수 있다. 복잡한 분산 트랜잭션과 아직 쓰이지 않는 범용 Artifact 관리 기능을 앞당겨 도입하지 않고, 실제 현재 Job/스토리지 경계에만 필요한 보상을 제공한다.

## 영향 및 한계

Worker 강제 종료, DB 장애 중 연결 실패, S3 전송 응답 소실 등의 경우 즉시 고아 객체가 없다고 보증하지 않는다. Job별 고유 키는 동일 Job 재시도 시 동일 경로를 사용한다. 장기적인 객체 목록 대조·보존 기한·정리 정책은 객체를 사용하는 Dataset 및 실제 작업 소유권을 확인하는 별도 운영 계약이 생길 때 결정한다.
