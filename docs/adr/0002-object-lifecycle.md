# 0002 — 객체 수명주기·장기 보존과 대조 정책

- 상태: Accepted
- 후속 결정: [0001 — 게시 일관성](0001-data-publication.md)
- 적용 영역: Data Workspace의 파일·결과물·Iceberg 참조

0001은 두 저장소 간 게시 성공과 실패의 원자성·보상 정책을 결정했다. 이 결정은 객체 생성 시점의 소유권, 장기 관측과 안전한 보존을 별도로 규정한다.

## 이전 게시 보상 결정의 개정

[ADR 0001](0001-data-publication.md)의 게시 성공 기준과 공유 원본 보호는 유지한다. 다만 그 결정의 **Transform 결과 객체를 실패 직후 보상 삭제한다는 조항**은 이 후속 결정으로 대체한다. DB 참조 부재만 검사해 즉시 삭제하면 게시·복구·재시도 간 경쟁 조건에서 데이터 손실이 발생할 수 있기 때문이다. 현재는 객체 게시 실패를 영속 기록하고 S3 객체를 보존하며, 별도 관측·권한·삭제 직전 재검증을 갖추기 전까지 실제 삭제를 제공하지 않는다.

## 객체 수명주기 및 정리 안전 계약

데이터를 저장하는 시점에 소유권과 참조 의미가 정해져야 하므로, 장기 정리 기능 구현 여부와 무관하게 다음 조건을 현재 계약으로 채택한다.

| 관리 대상 | 소유권·보존 기준 | 정리 권한 |
| --- | --- | --- |
| `datasets/` 콘텐츠 해시 원본 | 여러 Dataset이 공유 가능. 등록된 Dataset이 하나라도 참조하면 기한 없이 보존한다. DB 등록 실패 후 객체가 남을 수 있다. | Dataset 참조와 업로드 진행 여부를 모두 확인하기 전에는 삭제 금지 |
| `results/` Transform 산출물 | 성공 Job이 게시한 결과 Dataset 및 미완료 실행 시도가 보존 조건이다. 현재 키는 Job별이므로 동일 Job 재시도에서 재사용될 수 있다. | 해당 Job·Attempt와 게시 참조를 검증한 전용 정리 경로만 허용 |
| `iceberg/` 테이블 파일·메타데이터 | Iceberg Catalog, Snapshot, 참조된 Dataset 판본이 보존 조건이다. | 범용 S3 정리기로 직접 삭제 금지. Catalog의 Snapshot 만료·파일 정리 계약에서만 검토 |
| 로컬 `.sos/cache/`, `.sos/results/` | 다운로드 캐시는 재생성 가능하지만 실행 중 임시 파일은 소유 Worker가 있다. | 활성 Worker·실행 시도와 충돌하지 않는 별도의 로컬 정리 규칙으로 처리 |

### 게시와 참조의 원칙

1. PostgreSQL의 **확정된 Dataset 참조**는 게시 성공 여부의 정본이다. 단, DB 참조가 아직 없다는 사실만으로 객체를 삭제할 수는 없다. DB 기록 전 업로드·Worker 실행·장애 복구 단계에서 객체가 필요할 수 있기 때문이다.
2. 향후 자동 정리에는 **객체 생성 의도(write intent) → 전송 → 참조 확정 또는 실패 → 정리 후보**를 영속적으로 추적할 최소한의 소유권 기록이 선행되어야 한다. 필요한 식별자는 버킷·키, 객체 버전 또는 무결성 식별자, 생성 주체(Job/Attempt/Dataset), 생성·마지막 확인 시각, 상태, 보존 예외 및 판정 이력이다.
3. 동일 키를 재시도에서 덮어쓰는 현행 `results/{job_id}.parquet` 구조는 일반적인 비동기 정리기의 전제로 사용하지 않는다. 장기 운영 정리 기능 전에 **Attempt별 고유·불변 키**로 전환하거나 동등한 세대 식별 및 동시성 보호를 도입해야 한다.
4. 삭제 후보는 **참조 없음 + 진행 중인 게시/재시도 없음 + 충분한 대기 기간 + 반복 검증**을 모두 만족해야 한다. DB 접속 실패, 객체 버전 불명확, 활성 소유권 판단 실패, 다른 요청과의 경합이 있으면 삭제하지 않는다. 스캔 결과가 오래되었다면 삭제 직전에 다시 확인한다.
5. 데이터 보존 기한은 **참조된 Dataset/Job 결과**와 **미게시 임시 객체**를 구분한다. 참조 데이터에는 생성 시각만을 근거로 TTL을 적용하지 않는다. 미게시 객체의 초기 정리 후보 유예 기간은 **7일 이상**, **최소 24시간 간격의 두 번 이상 관측**을 설계 기준으로 삼는다. 이는 삭제 실행 허가가 아니라 후보 판정 기준이며, 향후 운영 규모와 보존 요구에 따라 설정·검증해야 한다.
6. 초기 운영 단계에서 S3 대조 결과는 **읽기 전용(dry-run) 보고**가 기본이다. 자동 삭제는 비활성화하며, 실제 삭제 기능을 도입할 경우 후보 키·발견 근거·크기·참조 상태·실행 주체·시각·결과를 감사 기록으로 남기고 승인·권한을 별도로 검증한다. 전체 버킷 삭제, 접두사 일괄 삭제, 보존 중인 Dataset 및 Iceberg 파일 직접 삭제는 허용하지 않는다.
7. Iceberg Snapshot 만료는 Dataset의 고정 Snapshot 참조를 깨뜨릴 수 있다. 따라서 만료 대상·기간을 정의하기 전에는 SOS가 생성한 Dataset 참조에 필요한 Snapshot의 보존을 우선한다.

### 구현 순서와 검증 경계

- **현재 PR:** 상기 소유권·보존·삭제 금지 계약을 확정한다. Job 게시 실패 시 삭제 대신 실패 의도를 영속 기록하고 원본 보존과 실패 주입 테스트를 유지한다. 범용 자동 삭제 스케줄러는 도입하지 않는다.
- **정리기 도입 전 필수:** 영속적인 업로드 의도/객체 소유권 및 Attempt별 결과 식별, S3 목록 대조의 페이지 처리·반복 실행·오류 보고, 재검증과 동시성 잠금, 감사 기록, 보존 예외 및 작업별 실효성 테스트를 구현한다.
- **안전성 검증:** 다른 Dataset이 공유하는 원본, 실행 중인 Job, 재시도된 결과, DB 장애, S3 목록 오류, Iceberg Snapshot 참조를 포함한 실패 주입 테스트에서 정리기가 참조 데이터를 삭제하지 않아야 한다.


## 현재 구현과 다음 단계의 경계

- 이 PR에서 구현하는 `object_writes`는 S3 쓰기 전에 생성 의도를 기록하고, Dataset 게시와 동일한 DB 트랜잭션에서 성공을 확정한다.
- 성공/실패 상태, Attempt별 결과 주소와 날짜 간 반복 관측, 읽기 전용 대조, Snapshot 참조 검사를 제공한다.
- 객체 정리 후보는 검토 상태일 뿐 삭제 승인이나 삭제 권한을 뜻하지 않는다. 자동 정리는 구현하지 않는다.
- 외부 저장소로 이동한 오래된 객체, 과거 게시 이력이 없는 객체, Iceberg Snapshot이 불확실한 객체는 삭제가 아니라 확인 필요 상태로 남긴다.
