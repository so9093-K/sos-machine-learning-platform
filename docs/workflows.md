# 워크플로

SOS는 데이터 처리, 학습, 평가, 모델 재사용, 추론, 관측·피드백을 연결한다. 각 과정은 독립적으로 사용할 수 있으며 **모든 작업을 단일한 선형 파이프라인으로 강제하지 않는다**.

## 실행 단위

- **Workflow Definition:** 여러 단계의 관계·입출력·조건을 표현하는 재사용 가능한 정의.
- **Workflow Run:** 정의를 실행한 한 기록. 여러 Job이 연결될 수 있다.
- **Job:** 사용자가 제출한 실행 요청과 최종 결과의 단위. 단독 Job도 가능하다.
- **Execution Attempt:** Job을 실제 수행한 개별 시도. 내부 재시도가 있더라도 이전 시도를 덮어쓰지 않는다.

각 개념의 자세한 의미는 [Contracts](contracts.md)가 정본이다.

## Job 상태 의미

| 상태 | 의미 |
| --- | --- |
| **Accepted** | 요청 검증을 통과해 플랫폼이 작업을 접수·기록함 |
| **Queued** | 실행 가능한 작업이 자원 또는 스케줄링을 기다림 |
| **Running** | 실행 시도가 실제 시작됨 |
| **Succeeded** | 정의된 성공 조건을 만족하고 결과가 확정됨 |
| **Failed** | 재시도 정책을 포함해 Job이 더 이상 성공할 수 없으며 실패가 확정됨 |
| **Cancelled** | 실행 중단 또는 시작 전 취소가 확인되어 종료됨 |

검증·권한 오류로 접수되지 않은 요청은 성공적으로 접수된 Job으로 표현하지 않는다. 구현에서는 중간 내부 상태를 더 둘 수 있지만, 외부에 노출하는 의미는 위 구분과 일치해야 한다.

- 상태 전이는 실제 작업 수행과 연결한다. 접수 또는 취소 **요청**만으로 작업 완료를 주장하지 않는다.
- **취소 요청은 종료 상태가 아니다.** 실제 취소가 확인되기 전에는 진행 상태와 취소 요청 사실을 구분한다. 완료와 취소가 경합하면 실제로 확정된 결과를 일관되게 기록한다.
- **재시도는 별도 Execution Attempt**로 추적한다. 시도가 실패했어도 재시도 가능하면 Job의 최종 Failed를 성급히 확정하지 않는다. 사용자에 의한 Fork·Reproduce는 원본 기록과 연결된 새로운 실행을 만든다.
- 지표나 진행률은 근거가 있을 때만 제공한다. 그렇지 않은 경우 실제 단계·시작 시각·현재 상태를 제공한다.
- 부분 결과·오류·진단 정보는 정책에 따라 보존하고, 상태와 결과를 서로 모순되게 노출하지 않는다.

## 연구에서 서비스로의 연결

데이터·전처리·모델 설정·Runtime을 바탕으로 실행을 만들고, 평가를 통해 모델 판본과 결과를 연결한다. 연구자는 실행을 비교하고 실패 조건을 이해하며 기록된 입력과 환경으로 재현한다. 적합한 모델을 추론 서비스 또는 외부 API에서 사용할 수 있고, 관측과 피드백을 다시 연구 입력으로 연결할 수 있어야 한다.

- 모델 등록과 배포는 동일한 사건이 아니다. 모델을 등록했다고 서비스 전환이 자동으로 일어났다고 간주하지 않는다.
- 데이터 스냅샷·모델 판본·평가 조건·아티팩트·Runtime 참조를 보존해 결과의 근거를 추적할 수 있어야 한다.
- 평가·모델 적용·서비스 배포는 필요에 따라 승인·검증 경계를 둘 수 있으나 특정 운영 절차를 현재 강제하지 않는다.
- 작업 실패는 API·사용자 경험에서 이해 가능한 원인과 다음 행동으로 연결한다. 사용자에게 보여주는 상호작용 기준은 [Experience](experience.md)를 따른다.

스케줄러, 큐, DAG 엔진, 저장소 제품은 실행 의미를 구현하는 선택이며, 이 정본의 특정 기술 의존성이 아니다.

## 데이터 작업의 중단과 재시도

일반 조회·변환과 달리 **Iceberg append는 외부 저장소 커밋이 발생하는 작업**이다. Worker가 중단됐을 때 커밋 여부가 불명확할 수 있으므로 이 경우에는 Job을 자동 재대기열에 넣지 않는다. 최종 Snapshot을 확인하고 중복 적재 위험을 검토한 뒤 사용자가 별도 실행하도록 한다.
